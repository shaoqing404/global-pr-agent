# 动态会话流与人机协作边界设计 (Dynamic Conversational Flow)

## 1. 为什么要做交互重构？
在早期的 Demo 中，系统的执行逻辑是“表单填写 -> 一脚油门踩到底”的伪智能（Pseudo-intelligence）模式。大模型在没有得到明确“放行”指令的情况下，极易擅自进入下一阶段，这剥夺了人类专家在复杂 PR 业务中的一票否决权，导致业务人员产生强烈的“失控感”。

为了打破这种线性流水线，发挥 Agent 真正的协同能力，我们引入了基于自然语言打断和迭代的机制，建立了真正的多轮控制权。

## 2. 三个核心改造点

### 2.1 状态锁死与无限次迭代机制 (Keyword Gating & Inner-Loop)
- **阶段护栏**：系统流程被严格划分为“任务计划”、“战略决策”、“洞察生成”和“审查反馈”。大模型无法单方面跨越这些阶段。
- **内循环微调**：用户可以通过自然语言对大模型当前输出的策略指指点点（例如：“把受众定位更年轻化一些”）。模型会重新生成当前阶段的内容，直到用户满意。
- **放行指令**：只有当系统捕获到显式的“硬指令”（如“确认策略”、“确认生成”）或触发相关的 UI 动作时，才会带着终稿策略放行到下一阶段。

### 2.2 专家审定机制的强化
在核心代码中，对 `Reviewers` 的 Prompt 进行了高压约束。专家不仅要打分，还必须强制挑刺（不能全盘说好），并给出明确的修改建议，从而为下一步的“反馈修改”阶段提供真实的对撞素材。

### 2.3 渲染层的彻底解禁
废弃了早期丑陋的纯文本或截断输出。全面拥抱大模型的原生 Markdown 输出（包含加粗、列表、层级标题），通过专业的解析器在前端呈现完美的富文本排版。

## 3. 跨终端 (Streamlit vs Vue) 实现建议
- **Streamlit 端**：由于框架限制，主要依赖用户手打 `[确认计划]`、`[确认策略]` 等硬关键词来触发 Gating 逻辑。
- **Vue 端**：利用前端框架的灵活性，应将“确认指令”转化为**动态的 UI 操作按钮 (Action Buttons)** 悬浮在消息气泡下方，既保留了严密的状态锁死逻辑，又免去了用户手敲指令的繁琐。
